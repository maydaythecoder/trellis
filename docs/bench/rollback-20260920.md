# Rollback hardening — 2026-09-20

v1.0 gate condition 4: *"induced mid-run failure returns the repo to its exact
pre-run state,"* proven at six or more injection points rather than the single
induced panic v0.2 shipped with.

`04-v1.0-harness.md` names the six and calls two of them the ones usually
missed. Both of those turned out to need code, not just a test.

| # | Injection point | Where | Result |
|---|---|---|---|
| 1 | Mid-edit, between two file writes | `trellis-vcs` | restored |
| 2 | Check subprocess killed mid-run | `trellis-vcs` | restored |
| 3 | After checks pass, before approval | `trellis-vcs` | restored, **and found an ordering hazard** |
| 4 | Trail write fails | `trellis-vcs` | restored |
| 5 | Orchestrator task ends | `trellis-loop` | **needed code** |
| 6 | **SIGINT mid-run** | `docs/bench/interrupt_test.sh` | **needed code**, verified with a real signal |

Plus the recovery path's own failure, which is task item 3 of the milestone and
is really a seventh injection point: what happens when `git reset --hard`
cannot do its job.

## 6 — SIGINT, the one that needed a real signal

There was no signal handling anywhere in the codebase. An unhandled SIGINT
kills the process with the run's edits still in the tree, which is the one
state TRELLIS promises never to leave — and because a run refuses to start on a
dirty worktree, the user's escape hatch became a wall for the *next* run too.

`Step::Done` is now raced against `tokio::signal::ctrl_c()`. Cancelling there
is safe precisely because of the actor design: the orchestrator is a separate
task owning the only write path, so dropping the loop's future cannot interrupt
a write half-done — it can only stop new ones being asked for.

On interrupt: roll back, record, exit **130** (the shell convention for SIGINT,
so a script can tell a deliberate abort from a failed run).

**Verified with a real signal**, which took some doing. `kill -INT` from Git
Bash on Windows raises no console Ctrl-C event for a native binary — three
attempts on this machine ran to completion with the signal never arriving, so
the test would have passed by never testing anything. It runs under WSL and in
CI on Linux, and the script refuses to be the Windows kind of green.

```
INTERRUPTED. Rolling back — nothing is accepted on an abort.
files this run had written: app/util.py

Rolled back to 8b1aa431. Worktree restored: true.
trail:    /tmp/.../.trellis/runs/20260920-192221-814-interrupt-me.json (interrupted; no turns recorded)
PASS: SIGINT rolled back, left a clean worktree, and recorded the run.
```

Mutation: replacing the `ctrl_c()` arm with a future that never completes makes
the run converge normally, exit 0, and leave the edit in the tree — the test
reports `FAIL: expected exit 130 (SIGINT), got 0`.

Two details the test had to get right, both of which made it silently useless
at first:

- **The log is written outside the repository.** An untracked `run.log` inside
  it made the worktree dirty, and TRELLIS refused to start.
- **Readiness is polled through `git status`, not the log.** The step list is
  printed when the run *ends*, so nothing appears in the log while the run is
  still going — which is the only moment this test cares about.

Determinism comes from the check command, not from timing a real type checker:
the fixture configures `typecheck` as a 30-second sleep, so the run is reliably
still going when the signal lands.

## 5 — a dead orchestrator

The danger `04-v1.0-harness.md` names here is "a panicking orchestrator task
must not leave a half-applied change set." It structurally cannot: the
orchestrator owns the only write path, so an orchestrator that is gone has
written nothing.

What was missing was *noticing*. `Handle::ask` already degrades safely — every
call returns its `on_dead` value — but degrading safely and noticing are
different things, and the loop read a dead actor as a model going nowhere,
spending the entire budget to discover that nothing works.

`Handle::is_alive()` and `NotConverged::OrchestratorGone` now stop the run at
the first unserved call. The message names this process rather than the
prompt, because a user told "the model could not continue" would go and rewrite
their task.

## 3 — the ordering hazard

Writing this test the obvious way failed, and the failure is the finding: a
trail **committed before the rollback is destroyed by it**. `reset --hard`
returns HEAD to the snapshot, which is behind the trail commit, so the record
of the run goes with it.

`cmd_run` already writes the trail after rolling back, with a comment saying
why. There is now a test under that comment.

## The recovery path's own failure

Three changes, because a failure on the path that exists to recover from
failure must never be quiet:

- **`rollback` attempts both steps even when the first fails.** A `clean` that
  succeeds after a failed `reset` removes this run's new files, which is
  strictly better than leaving both kinds of residue.
- **`VcsError::RollbackFailed` carries the way out**: it names the worktree,
  gives the exact commands rather than describing them, and says what to
  suspect when those also fail (a held `.git/index.lock`, a read-only mount).
- **A failed rollback no longer swallows the trail.** `cmd_run` used `?` here,
  so the one run whose record matters most — the tree is in an unknown state —
  was the one run that never got a trail written.

Exit codes now distinguish the cases: **1** the run did not converge and the
tree is back as it was; **2** the tree is *not* back, which a wrapping script
must not treat as an ordinary failed run; **130** a deliberate abort.

### And the string-folding defect, a sixth time

The first version of the `RollbackFailed` message was a multi-line literal in
the `#[error(...)]` attribute, which picked up the source indentation of every
continuation line. My own assertion caught it —

```
"no folded indentation in text a user reads under pressure"
```

— which is the first time that defect has been caught by a test rather than by
reading output. The text is built in a function now, and the assertion stays.

## Reproducing

```
cargo test -p trellis-vcs -- rollback_ a_rollback_that_fails
cargo test -p trellis-loop -- a_dead_orchestrator
cargo test -p trellis-cli  -- interrupt_tests

# the real signal, on a POSIX host
cargo build --release -p trellis-cli
bash docs/bench/interrupt_test.sh "$PWD/target/release/trellis"
```

All of these run in CI as `rollback-gate`.

## What this does not establish

Power loss and a killed process (SIGKILL) are not covered and cannot be: both
skip the handler by definition. What protects those is the same property that
makes the rest work — no run ever commits the code it proposed, so the worst
case is a dirty worktree the user can reset, and TRELLIS refuses to start on
one rather than compounding it.
