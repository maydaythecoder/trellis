# Run views converge on facts, not verdicts

Across sixteen shipped agent harnesses and the 2025–2026 oversight literature, the run view that holds up is a stack of plain facts: a coarse state word with a count-up clock and an "-ing" activity line, a queue of pending operator messages that says exactly when each will land, a transcript whose rows are typed by role with reasoning folded away by default, consumption shown as two numbers against a ceiling, and a diff that doubles as the end-of-run summary. No tool in the set emits a correctness verdict at the end of a run and none lets the operator edit a budget while the run continues; caps are set at launch (Claude Code's `--max-budget-usd` is print-mode only, Goose's `--max-turns`, OpenHands' `max_budget_per_task`) or held at the account level (Devin ACUs, Codex and Claude plan limits). The queue designs have settled on three verbs, queue, steer and interrupt, with VS Code exposing all three in one dropdown and Warp alone documenting drag-reorder. The strongest controlled evidence (IJCAI-26, N=16) shows that separating "Thought" from "Action" and keeping the plan as a persistent checklist cut time-to-insight by 56% against a linear trace, while two larger experiments (N=752, N=800) show that prominent reasoning raises agreement without raising error detection and that confident phrasing suppresses it. For TRELLIS this lands cleanly on its existing rules: the client draws what `trellis rpc` reports, names an unreported figure as unreported, keeps `Verified` and `Reviewed` as two counts, shows check rows only when `trellis-checks` produced a `Verdict`, and never labels anything "complete" or "verified" on its own authority. The one place the market is empty, a mid-run editable budget, is also the one place the design has to be invented rather than borrowed, and the evidence says to record any such edit in the trail as a user action and state its consequence before applying it.

## Running state is a verb and a count-up clock, not a percentage

The shipped tools agree on the shape of the live indicator even where their documentation is thin. Claude Code's is the most fully specified: a spinner line ending in elapsed time and a live output-token count, `Deciphering… (10m 27s · ↓ 5.5k tokens)`, where the arrow points down while output arrives and the count resets each turn and at compaction ([Claude Code docs: costs](https://code.claude.com/docs/en/costs.md)). Beneath it sits a footer with `esc to interrupt` and an optional shell-scripted status line fed JSON fields such as `cost.total_cost_usd`, `cost.total_duration_ms`, `context_window.used_percentage` and `cost.total_lines_added` ([Claude Code docs: status line](https://code.claude.com/docs/en/statusline.md)). Codex CLI composes its footer from a TOML array of named items (`model`, `approval`, `context_usage`, `spinner`, `sandbox`, `cwd`) and reads `100% context left · ? for shortcuts` in the official sample screen ([Codex CLI docs](https://learn.chatgpt.com/docs/codex/cli); [codex.danielvaughan.com, TUI customisation](https://codex.danielvaughan.com/2026/05/05/codex-cli-tui-customisation-keymaps-themes-status-lines/)). Amp shows thread cost while working ([developersdigest.tech Amp reference](https://www.developersdigest.tech/reference/amp)); Warp calls its indicator the "warping indicator" and hangs the auto-queue toggle on it ([Warp docs: prompt queueing](https://docs.warp.dev/agents/local-agents/interacting-with-agents/prompt-queueing/)). Goose's working indicator is undocumented on every page the researchers could reach, and Codex's exact spinner text and whether it shows elapsed time were not found; those are gaps, not absences.

The IDE panels treat elapsed time as diagnostic rather than primary. VS Code shows request and completion timestamps only under `chat.verbose`, with elapsed time on hover, and offers a persistent progress animation that is off by default in Stable ([VS Code docs: chat agent mode](https://code.visualstudio.com/docs/copilot/chat/chat-agent-mode)). Roo Code documents a spinner with errors in red and successes in green ([Roo Code docs: chat interface](https://roocodeinc.github.io/Roo-Code/basic-usage/the-chat-interface)); Cline tracks tokens, cost and execution time in a task header with a hoverable block timeline of tool calls and edits ([Cline docs: task management](https://docs.cline.bot/core-workflows/task-management); [Cline blog: v3.15](https://cline.bot/blog/cline-v3-15-unveiling-task-timeline-gemini-implicit-caching-new-community-docs)). The autonomous dashboards go further on state vocabulary than on timing. OpenHands' frontend maps thirteen agent states to colours, RUNNING green, AWAITING_USER_INPUT blue, AWAITING_USER_CONFIRMATION orange, PAUSED yellow, STOPPED and ERROR red ([OpenHands frontend state map, mirror](https://huggingface.co/spaces/Backup-bdg/OpenHands/blob/main/frontend/src/components/agent-status-map.constant.ts)). Claude Code's agent view groups sessions under Working, Needs input, Ready for review and Completed, encodes state in icon colour and process liveness in icon shape (`✻` alive, `∙` exited), and prints one activity line per row with an age that freezes at the run's duration when the run ends, e.g. `✽ collision detection   Adding swept-AABB checks to CollisionSystem   2m` ([Claude Code docs: agent view](https://code.claude.com/docs/en/agent-view.md)). Its peek panel adds `waiting 3m` for a blocked session. Jules reports `Total runtime` only at completion ([Jules docs: running tasks](https://jules.google/docs/running-tasks.md)). No tool in the set documents a current-file readout in its status area; "where it is" is conveyed by the latest tool card at the bottom of the transcript, by Zed's follow-the-agent crosshair that scrolls the editor to the file being edited ([Zed docs: agent panel](https://zed.dev/docs/ai/agent-panel)), or by a checklist (Claude Code's `Ctrl+T` task list of up to five items ([Claude Code docs: interactive mode](https://code.claude.com/docs/en/interactive-mode.md))).

The HCI evidence explains why count-up won. NN/g's guidance says anything over ten seconds needs determinate progress or a step count and a cancel control, and that a promised time that is missed damages trust ([NN/g, progress indicators](https://nngroup.com/articles/progress-indicators)). Fluent 2 tells conversational-AI designers to "indicate that the process is still active rather than estimating time, since timing is unpredictable," to label in-progress states with "-ing" verbs and completed ones in past tense, and to announce state changes with `role="status"` ([Fluent 2 Wait UX](https://fluent2.microsoft.design/wait-ux)). The CHI 2026 "Counting the Wait" experiment (N=425) found that no time display made waits feel longer than a countdown, but that countdowns produced more frustration than an elapsed-time display (30.7 vs 24.1, p=.019), and its authors recommend qualitative cues over countdowns for unpredictable delays ([Tan and Nov 2026](https://arxiv.org/pdf/2602.04138)). Microsoft's interview study of 17 professional developers found they "relied on cues like long run times to spot context drift rather than systematic monitoring" and recommends surfacing elapsed time as a first-class signal ([Dhanorkar, Passi, Vorvoreanu 2026](https://www.alphaxiv.org/abs/2606.05391.md)). Put together: a TRELLIS run header should show the state word, a count-up clock driven by the client's own tick, an activity line in present participle form taken from the last event, and no remaining-time estimate unless it is derived from a measurable ceiling. The Go TUI already does the first two: its budget line follows the driver's clock while running and names a figure trellis did not report rather than drawing 0 (`tui/internal/view/view.go` line 428; the `TestBudgetLineUnreportedFiguresAreNamedNotDrawnAsZero` test). The research adds the vocabulary rule, that a state set of working, needs input (with the reason), stopped (with the reason) and ended (with the exit code) is assembled from the evidence, not copied from any single tool, and that "waiting on you" deserves its own colour and its own reason line everywhere it is documented.

## Queues settle on three verbs, and the application point must be visible

Nearly every tool now accepts input while a turn runs, and they have converged on three operator verbs: queue (deliver when the turn ends), steer (deliver at the next tool boundary) and interrupt (stop now and send). VS Code puts all three in one Send dropdown, Add to Queue, Steer with Message and Stop and Send, with a drag handle to reorder pending messages of the same type and a `chat.requestQueuing.defaultAction` setting ([VS Code docs: chat agent mode](https://code.visualstudio.com/docs/copilot/chat/chat-agent-mode)). Zed queues by default, adds a per-message Steer toggle that fires "usually between a tool call and a response," and lets each queued message be edited or removed ([Zed docs: agent panel](https://zed.dev/docs/ai/agent-panel)). Claude Code queues on Enter, renders sent-but-unstarted messages in gray inside the conversation, delivers queued text "as soon as those tool calls finish, within the same turn," sends now on `Ctrl+Enter`, and lets `Up` take the whole queue back into the input box one entry per line ([Claude Code docs: interactive mode](https://code.claude.com/docs/en/interactive-mode.md)). Codex and Amp invert the default: Enter steers and `Tab` (Codex) or a palette command (Amp) queues ([codex.danielvaughan.com, TUI reference](https://codex.danielvaughan.com/2026/04/08/codex-cli-tui-shortcuts-slash-commands/); [ampcode.com keybindings](https://ampcode.com/docs/cli/keybindings)). Warp has the richest queue surface: a collapsible panel between the indicator and the input whose header counts `2 queued`, drag-reorder, pencil edit, trash delete that returns the text to the input, send-now, and a `(queued until the command finishes)` annotation while an agent-started command runs ([Warp docs: prompt queueing](https://docs.warp.dev/agents/local-agents/interacting-with-agents/prompt-queueing/)). Roo Code shows a bordered card per entry under the label "Queued Messages:" ([Roo Code docs: message queueing](https://roocodeinc.github.io/Roo-Code/features/message-queueing/)). On the web, Claude Code marks a queued message with a ✕ that returns the text to the box unless Claude has already read it ([Claude Code docs: cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)), and Copilot's coding agent offers a single prompt box below the log whose message "applies after finishing its current tool call" ([GitHub docs: track Copilot sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)). Aider has no queue; Cursor's CLI explicitly does not support one ([Cursor forum](https://forum.cursor.com/t/cursor-agent-send-queued-message/147962)); Cline, Continue, Junie and Goose document nothing.

| Tool | Default on Enter | Queue | Steer | Reorder / edit | How the queue is drawn |
|---|---|---|---|---|---|
| Claude Code CLI | queue | Enter | `Ctrl+Enter` send now | `Up` takes back all | gray rows in the transcript |
| Codex CLI | steer | `Tab` | Enter | not documented | not documented |
| Amp | steer | palette `prompt: queue message` | Enter; `Enter Enter` on queued | `↑`/`↓` to edit | not documented |
| Warp | interrupt | `/queue`, auto-queue toggle | new prompt in Interrupt mode | drag handle, pencil, trash | "N queued" panel, top row sends next |
| VS Code Copilot | configurable | Add to Queue | Steer with Message | drag handle | pending list above input |
| Zed | queue | Enter | per-message Steer toggle | edit/remove each | not documented |
| Roo Code | queue | Enter | none | click to edit, trash | bordered cards, "Queued Messages:" |
| Claude Code web | queue | send | none | ✕ returns text | card with ✕ |

Two hazards in the record matter more than the feature list. Roo Code's documentation warns that a processed queued message "implicitly approves the next pending action" even with auto-approval off ([Roo Code docs: message queueing](https://roocodeinc.github.io/Roo-Code/features/message-queueing/)), a semantics no other tool states and one a harness copying the pattern must decide explicitly. Cursor's forum carries five regression threads between October 2025 and February 2026 about queued messages interrupting, stalling or arriving out of order, and a staff reply acknowledging "past regressions in the message queue" ([Cursor forum](https://forum.cursor.com/t/messages-always-queueing-now/151759)), which suggests "deliver at the next ideal time" is hard to make reliable and that users notice when a message waits until the end instead. Microsoft's developers reported that "Redirecting an agent often failed, so developers had to stop it and restart" ([Dhanorkar, Passi, Vorvoreanu 2026](https://www.alphaxiv.org/abs/2606.05391.md)). The literature has no empirical study of queued next-instructions at all; the practice exists without published evaluation.

The inference for TRELLIS follows from those failures rather than from any one product: a steer must be shown with its point of application and, once delivered, with the turn it reached, so the operator can tell "queued" from "landed" from "too late." TRELLIS already builds this: a line typed mid-run leaves on the steer channel, is drawn queued then delivered, is numbered in order and names the turn it reached, and a steer that arrives after the task ended is reported as not delivered rather than silently dropped (`tui/PARITY.md`, the `TestSteerDeliveredOnceAtItsTurn` and `TestSteerAnswersMarkItDeliveredOrNot` rows). It also holds that a steer "never marks a check or an edit" (ADR 0004), which is the structural answer to Roo's implicit-approval hazard: a queued operator message is text for the model, never an approval. What the wireframe should add from Warp and Claude Code is the take-back path (a queued steer returns to the composer, not to the void) and a visible count in the header while anything is pending. Reordering is a Warp-only feature with no evidence behind it and the TRELLIS steer channel is sequential by design; it is reasonable to leave it out and say so.

## Transcripts separate roles by structure, and reasoning belongs behind a disclosure

The common grammar across the IDE panels is a user prompt rendered as an editable card (Zed, VS Code, Cline), model prose as plain markdown, reasoning as a collapsed subordinate block, each tool call as a card carrying its own approval controls and expand toggle, and the tool's result nested inside it; colour is reserved for diff lines and error or success states rather than for distinguishing roles. VS Code collapses completed work into "Completed N steps" sections, renders reasoning in "separate collapsible previews," and lets Find expand a section when a match is inside it ([VS Code docs: chat overview](https://code.visualstudio.com/docs/chat/chat-overview)). Zed draws tool permission requests as "a tool card with a menu" and inserts an expandable "Context Compacted" entry into the thread ([Zed docs: tool permissions](https://zed.dev/docs/ai/tool-permissions)). Cline shows each proposed change with its file path, the code, a checkmark and an X, with checkpoint markers as bookmark icons linking to Compare and Restore ([Cline docs: IDE tutorial](https://docs.cline.bot/usage/ide.md); [Cline docs: checkpoints](https://docs.cline.bot/core-workflows/checkpoints)). The terminal tools default to collapse: Claude Code folds tool detail behind `Ctrl+O`, shows MCP calls as a single `Called slack 3 times` line, and stamps each assistant message with its timestamp and model in the transcript viewer ([Claude Code docs: interactive mode](https://code.claude.com/docs/en/interactive-mode.md)); Amp hides thinking and tool blocks until `Alt+T` ([ampcode.com keybindings](https://ampcode.com/docs/cli/keybindings)); Goose shortens tool output unless `/r` toggles it ([linuru.com goose](https://linuru.com/goose/)); Codex keeps a separate transcript overlay on `Ctrl+T` and a `hide_agent_reasoning` switch ([Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). Aider is the only tool that documents per-role colours as settable defaults, user `#00cc00`, assistant `#0088ff`, tool error `#FF2222`, tool warning `#FFA500` ([aider.chat options](https://aider.chat/docs/config/options.html)). The autonomous dashboards separate by surface instead: Devin's Progress tab unifies shell, edits and browser as clickable steps beside a narrative chat ([Devin docs: session tools](https://docs.devin.ai/work-with-devin/devin-session-tools.md)); OpenHands keeps Chat, Terminal, Browser, Changes and VS Code as tabs ([OpenHands docs: key features](https://docs.openhands.dev/openhands/usage/key-features)); Jules appends each completed step to an activity feed with a mini diff per file ([Jules docs: running tasks](https://jules.google/docs/running-tasks.md)). Only the post-hoc viewers give an explicit detail dial: LangGraph Studio's slider and Show tool calls toggle ([LangSmith docs: use Studio](https://docs.langchain.com/langsmith/use-studio.md)), SWE-agent's inspector `v` key between reduced and full ([SWE-agent docs: inspector](https://github.com/SWE-agent/SWE-agent/blob/main/docs/usage/inspector.md)). No reachable source gave the literal glyphs any tool uses to prefix user, assistant and tool lines; the wireframe will have to pick its own.

The evidence for this layout is stronger than the evidence for any individual control. The IJCAI-26 demonstration paper proposes a persistent TODO checklist, a "BrainPanel" that streams "Thought" separately from "Action," a grid of sub-agent cards and a read-only live filesystem view; in a 16-engineer between-subjects study, time-to-insight fell from 5.5 to 2.4 minutes (56%, d=1.05, p=0.004) and NASA-TLX load from 64.8 to 43.7 against LangSmith's linear trace, with participants attributing the gain to "visually verifying execution instead of reconstructing state from linear traces" ([IJCAI-26 paper 987](https://www.ijcai.org/proceedings/2026/0987.pdf)). Data & Society quantifies the alternative: one five-agent run produced 90 inter-agent messages totalling about 7,230 words, "which the authors compare to a research paper" ([Data & Society, The Oversight Fallacy](https://datasociety.net/wp-content/uploads/2026/07/the-oversight-fallacy-layout-final.pdf)). Microsoft's developers "mostly skimmed logs or traces" and found reviewing agent code "slow and shallow," with "each new iteration" requiring "a full re-review" ([Dhanorkar, Passi, Vorvoreanu 2026](https://www.alphaxiv.org/abs/2606.05391.md)). Four panels of parallel work map directly onto a TRELLIS run: plan, step log, partition cards and worktree diff.

The case for folding reasoning away by default is not aesthetic. Chen, Gao and Liang's preregistered N=752 experiment found that showing AI reasoning raised agreement with the AI and, when participants held knowledge the AI lacked, their agreement dropped 11.5 points without reasoning but only 8.7 to 9.0 with it, which the authors read as over-trust that "crowds out" human knowledge; shortening the reasoning did not help ([Chen, Gao, Liang 2025](https://arxiv.org/pdf/2511.04050)). Park et al. (N=800) found agreement and trust correlated at r=+0.82 and both negatively correlated with error detection; omitted-step reasoning was caught only 31% of the time, and confident phrasing lowered detection on incorrect verdicts from 62.3% to 52.0% while trust barely moved ([Park et al. 2025](https://arxiv.org/pdf/2511.12001)). One developer in the Microsoft study estimated 10% of the agent's self-explanations were wrong: "It is very confident, so you don't get to know" ([Dhanorkar, Passi, Vorvoreanu 2026](https://www.alphaxiv.org/abs/2606.05391.md)). Both trust experiments used lay crowdworkers on classification tasks, not developers reviewing runs, so whether experts over-trust the same way is untested, but the direction is consistent across three sources. IBM Carbon's layered explainability, a label as entry point, a popover as the first layer, deeper detail only on request, is the design-system expression of the same rule ([Carbon for AI](https://carbondesignsystem.com/guidelines/carbon-for-ai/)).

For TRELLIS this fixes the row types of the action log and their default visibility. Operator prompts and steers are one visual class, distinct from model text; tool calls and their results are a second class, collapsed to one line each with the file or command named; the model's reasoning, where the adapter reports it, is a third class folded by default; and check results are a fourth class that comes only from `trellis-checks`. The TUI's rule that check rows "come only from a Some verdict" (`TestPanesCheckRowsComeOnlyFromASomeVerdict`) is exactly what Park's finding demands: the row the reviewer's eye lands on is a recorded fact about a process exit, never a model sentence. The same finding argues against any status wording that functions as a booster. "Verified," "complete" and "all tests pass" are the words models use most and the words that suppress scrutiny; the supported form is the neutral past-tense fact with its scope, `pytest: 212 passed, 0 failed, 3 skipped on 14 files` and, beside it, what was not checked. That is also the CLAUDE.md rule against marketing language restated as an HCI finding.

## Budgets are fixed at launch everywhere; nobody ships a mid-run editor

This is the thinnest area of both the product record and the literature, and the gap is itself the finding. Claude Code's `--max-turns` and `--max-budget-usd` are print-mode only; when spend reaches the cap, spawning another subagent fails with `Budget limit reached` and running subagents are stopped ([Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference.md)). The closest it comes to editing mid-run is a prompt to raise a plan spend limit when it is hit, and `/effort` or `/model` changes that apply to the next request of the current turn ([Claude Code docs: costs](https://code.claude.com/docs/en/costs.md); [Claude Code docs: interactive mode](https://code.claude.com/docs/en/interactive-mode.md)). Codex's `features.rollout_budget.limit_tokens` is "under development and off by default," with a reminder interval defaulting to 10% of the limit ([Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). Goose takes `--max-turns` and `--max-tool-repetitions` and has a Max Turns setting ([goose-session man page](https://www.mankier.com/1/goose-session)). OpenHands' legacy V0 config carries `max_iterations` (default 100) and `max_budget_per_task` (default 0.0, meaning no limit), and the V1 docs no longer list either ([OpenHands V0 configuration](https://docs.openhands.dev/openhands/usage/v0/advanced/V0_configuration-options.md)). In the IDEs, the only numeric cap is Roo Code's Max Requests, which pauses before request N+1 with a "Reset and Continue" prompt ([Roo Code docs: rate limits and costs](https://roocodeinc.github.io/Roo-Code/advanced-usage/rate-limits-costs)); VS Code's historical `chat.agent.maxRequests` was absent from every page fetched. Devin's ACU limits live in enterprise admin settings, reset monthly, and the docs "do not say whether the user receives a warning or whether a running session pauses" ([Devin docs: ACU limits](https://docs.devin.ai/admin/billing/acu-limits.md)); Codex cloud tasks and Claude Code web sessions draw on account-level plan allowances with no per-session cap ([Flavio Copes, Codex cloud](https://flaviocopes.com/codex-cloud/); [Claude Code docs: cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)). What the products do show live is consumption rather than an editable ceiling: Cline's header cost updated after each request ([Cline docs: task management](https://docs.cline.bot/core-workflows/task-management)), Roo's per-request cost beside token usage, Zed's thread token count near the profile selector ([Zed docs: agent panel](https://zed.dev/docs/ai/agent-panel)), Junie's context percentage and token count ([Junie docs](https://junie.jetbrains.com/docs/junie-ide-plugin.html)). Approval scope is the control that does move mid-run: Claude Code's `Shift+Tab` permission modes, changeable on the web "while the session runs" ([Claude Code docs: cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md)), Roo's Enabled toggle that pauses auto-approval, and Hedwig's revocable per-preference grants ([Hedwig](https://arxiv.org/pdf/2605.11495)).

The literature offers principles, not studies. No published HCI work on budget display for autonomous agents was found. The applicable guidance is HAX G16, "Convey the consequences of user actions," and G17, "Provide global controls" ([HAX Design Library](https://www.microsoft.com/en-us/haxtoolkit/library/example,guideline/7,17/)); Data & Society's request for "actionable steering: intuitive controls, plus guidance on what settings do and when to use them" ([Data & Society, The Oversight Fallacy](https://datasociety.net/wp-content/uploads/2026/07/the-oversight-fallacy-layout-final.pdf)); and NN/g's preference for determinate progress once a wait is long ([NN/g, progress indicators](https://nngroup.com/articles/progress-indicators)). Budget consumption is the one measurable quantity in an otherwise indeterminate run, which makes it the natural determinate indicator, shown as consumed and ceiling as two numbers rather than as a synthetic percent-complete.

TRELLIS's rules make three things concrete that no competitor had to decide. First, an unreported figure is named, never drawn as 0, which the loop already enforces: once any model call goes unreported the token sum is reported as unknown "rather than the partial sum" (`crates/trellis-loop/src/adapter.rs` lines 547–550), and the Go TUI draws no rate and no queue wait when tokens were not reported (`TestBudgetLineWithoutTokensDrawsNoRateAndNoWait`). A budget widget therefore has to be able to render "tokens: unreported · ceiling 200k" and not an empty bar. Second, budgets divide across partitions and never multiply (CLAUDE.md rule 9), so a per-partition card shows its share of the ceiling and the run header shows the whole, never a sum of per-partition remainders. Third, if TRELLIS adds an editable ceiling mid-run, it would be shipping something none of the sixteen tools documents; the design that follows from G16 and from rule 10 (trails read back as untrusted data) is that the edit is a user action written to the trail with the old and new value and the turn at which it took effect, the control states its consequence before applying ("raising the ceiling lets the current task continue; lowering it below what is consumed ends the run not converged and rolls back"), and the client sends the edit through `trellis rpc` and draws the ceiling trellis echoes back, not the number the user typed. That last point is the general rule for the whole view: the client computes nothing; it asks and it draws what it is told.

## Diffs are the summary, and the only "verified" badge in the field is a git signature

In every product with a documented end state, the diff is the end-of-run summary and the PR is a button on it. Claude Code's `/diff` panel opens beside the conversation at 110 columns or more, lists changed files with added and removed line counts, refreshes after each edit or shell command, offers a `source` picker between per-turn views `T1`, `T2`, … and `Current`, and has an `ask` button that attaches a file's diff to the next prompt; its turn views "come from Claude's file edits rather than from git, so a change Claude makes through a shell command appears only under `Current`" ([Claude Code docs: interactive mode](https://code.claude.com/docs/en/interactive-mode.md)). On the web each session shows `+42 -18`, a file list beside the changes, inline comments that "queue up until you send your next message, then they're bundled with it," and a Create PR button; the session stays live after the PR exists ([Claude Code docs: cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md); [Claude Code web quickstart](https://code.claude.com/docs/en/web-quickstart.md)). Codex has `/diff` over the working tree and `/review` with presets for base branch, uncommitted changes or a commit, running "without modifying your working tree" ([Codex CLI docs](https://learn.chatgpt.com/docs/codex/cli)), and its desktop Review pane stages or reverts chunks ([codex.danielvaughan.com, app workspace](https://codex.danielvaughan.com/2026/04/17/codex-app-workspace-pr-review-task-sidebar-artifact-viewer/)). Aider shows diffs as it edits and commits every change by default with `/undo` to reverse the last commit ([aider.chat commands](https://aider.chat/docs/usage/commands.html)). Per-hunk accept and reject is an IDE affordance: Zed's Review Changes multibuffer accepts or rejects "each change hunk, or the whole set" ([Zed docs: agent panel](https://zed.dev/docs/ai/agent-panel)); VS Code marks pending edits with a squared dot, gives Keep and Undo per change and per file, and has a time-based `autoAcceptDelay` that pauses while the overlay is hovered ([VS Code docs: review code edits](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)); Cursor's floating review bar accepts or rejects per file, and its forum records the review model oscillating between inline Keep/Undo and a consolidated Review panel for six months until an Inline Diffs setting selected between them ([Cursor docs: review](https://docs.cursor.com/agent/review); [Cursor forum](https://forum.cursor.com/t/per-change-keep-undo-buttons-missing-after-agent-edits-only-undo-all-available/158983)). Cline and Roo approve each edit before it lands and review after the fact through checkpoint Compare. Jules is the only tool with a structured completion card: Files changed, Total runtime, Lines of code added/changed/removed, Create branch ([Jules docs: running tasks](https://jules.google/docs/running-tasks.md)). Devin's post-hoc Session Insights analyses the session's health (ACU usage, user messages, session size XS–XL, an issue timeline), not the code ([Devin docs: session insights](https://docs.devin.ai/product-guides/session-insights.md)).

What none of them has is a structured record of what was checked. Test results appear in the transcript as tool calls or in prose, "Review changed files and test results" ([Codex cloud docs](https://learn.chatgpt.com/docs/cloud.md)); Claude Code's `/usage` block reports cost, API and wall duration, lines added and removed, and tokens by model, but no verdict ([Claude Code docs: costs](https://code.claude.com/docs/en/costs.md)); Claude Code's recap is a 400-character narrative. The word "Verified" does appear once, on Copilot coding agent's commits, where it means a signed commit, not a checked change ([GitHub docs: track Copilot sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)). Wang et al. supply the reason that gap matters: over 50% of test-passing patches in their sample were flagged by annotators as functionally different from the gold patch, about 20% missing functionality and over 10% including unrelated changes, and they recommend that verification "surface evidence in human-interpretable ways" rather than rest on unit tests ([Wang et al. 2026](https://arxiv.org/pdf/2608.12355)). Microsoft's developers already behave as if that were true: "Plans become proxies for agentic working, test results stand in for code correctness" ([Dhanorkar, Passi, Vorvoreanu 2026](https://www.alphaxiv.org/abs/2606.05391.md)).

TRELLIS's diff and completion surfaces should borrow the mechanics and refuse the vocabulary. From Claude Code: a diff pane that stays open and refreshes, per-turn attribution so a reviewer can answer "what changed since I last looked," a comparison base picker, and line-level comments that become the next steer. From Zed and VS Code: a changed-files list with two line counts per file and a keyboard path through hunks. From Jules: a completion card of facts. The refusals are TRELLIS-specific and each has a test behind it. The card reports the run's exit code rather than a verdict (`TestModelRunEndSetsTheOutcome`). The checks block lists each `RecordedCheck` by name with its exit status and the scope it ran over, and a failing check "says failed and is not recorded as a pass." The coverage block shows `Verified` and `Reviewed` as two labelled counts on separate lines with no sum, because `ModeCounts` has no `total()` (ADR 0003), and shows the blast radius as three counts with no ratio (ADR 0014). Where coverage data was absent, the block says "not measured," since `docs/STATUS.md` already notes that zero counts with no coverage file mean not measured, not zero. Per-hunk accept and reject is a decision rather than a borrowing: TRELLIS's approval modal keeps the question drawn while a 60-line diff scrolls (`TestApproveModalKeepsTheQuestionDrawnWhileTheDiffScrolls`) and answers with `y` or `n`; adding hunk-level keep and undo would move an edit decision into the client, and the client must not become a writer that the rollback rules do not cover (ADR 0032). The conservative choice, stated in the report rather than silently taken, is approval per proposed edit with a full diff, and post-hoc review through the trail, until an ADR says otherwise.

Three items are deliberately absent because the evidence does not support them: a percent-complete bar (no measurable denominator; CHI 2026 and NN/g both warn against invented estimates), a remaining-time estimate, and a prominent reasoning stream (Chen and Park). Three items are deliberately absent because the record is empty and the report says so: queue reordering (Warp-only, unevaluated), a mid-run budget editor (no shipped tool, no study; if built, trail it as a user action and state its consequence first), and a current-file readout in the header (no tool documents one; the latest tool-call row is where every product puts it). Two sources that might have changed these findings could not be read: AgentGUI (arXiv 2607.26300), whose title claims observing and steering long-running agents, returned no machine-readable text, and Google's PAIR Guidebook returned only metadata. Goose's live indicator, Codex's spinner text and Amp's queue rendering are undocumented on every reachable page, which is reported here as unreported rather than as absent.

## Conclusion

The sixteen tools disagree on keybindings and agree on substance: the operator needs a state word, a clock, a place to type the next thing with proof of when it landed, a log whose row types are visible at a glance, and a diff. The field's unsolved problems are the ones TRELLIS's rules already address at the type level. No product shows what was checked as a structured fact distinct from what the model said; no product distinguishes a figure of zero from a figure never reported; no product keeps two coverage populations from being folded into one number. Those are not features TRELLIS is missing but constraints the rest of the market has not yet adopted, and the trust experiments say the market's defaults, prominent reasoning and confident status words, are making reviewers worse at catching errors. A run view that draws only reported facts and labels every absence is therefore not a stylistic preference; it is the design the oversight evidence recommends.

What changes going forward is where the design effort should go. Borrowing is cheap for the header, the queue, the collapsed log and the diff pane, since the patterns are stable and the TUI already holds most of them under test. The budget widget and the completion card are where TRELLIS leaves the map: the first because it would be the only harness with a mid-run ceiling edit, the second because it would be the only one whose summary is a list of recorded checks and two separate coverage counts rather than a narrative. Both should be wireframed first against the question the Data & Society primer poses, whether the control beside the fact gives the operator enough to decide, and both should be tested the way the harness tests everything else, by a named test that fails when an unreported figure is drawn as zero or a client row claims a pass that `trellis-checks` never issued.
