# v1.1 — Multi-agent

Several agents working concurrently on one task. This is where the index earns
its keep beyond blast radius: it is what lets you decide *safely* which work
can run in parallel.

**Gate:** a change that decomposes into three or more disjoint partitions
completes correctly in parallel, with a deliberately-induced cross-partition
collision caught by the integrated check and recorded as a suspected recall
gap.

Status: **partitioning machinery built at N=1.** The planner and its
disjointness invariant exist and are property-tested over 400 seeds.
`Supervisor::run_plan` can run a staged plan's parallel stage in worktrees
(ADR 0037); the CLI does not enable N>1. This is deliberate — N=1 is the degenerate case, built
early so the architecture is right, and N>1 waits until the single-agent
numbers exist.

---

## The rule

**Agents parallelize work, never judgment.** No agent reviews another's output
for correctness. Verdicts still come only from `trellis-checks`.

Constraint 2 is why. Parallel work multiplies throughput; parallel judgment
multiplies error — a scaling study measured independent multi-agent topologies
amplifying errors 17.2-fold versus a single agent, with centralized
coordination containing it to 4.4-fold. Keep coordination centralized and
judgment mechanical.

---

## Partition by blast radius

Given a task decomposing into N units, compute each unit's radius and group
units whose radii do not intersect. Two partitions are compatible when their
`radius` sets **and** their `files` sets are both disjoint. Files matter
separately: two symbols in one file cannot be edited by two agents without a
merge conflict, even with disjoint call graphs.

Each partition gets its own git worktree, branched from the run's base commit,
with its own index snapshot. Real filesystem isolation for free, and rollback
per partition is deleting a directory.

The orchestrator stays single-owner: it owns the *master* index and the
integration; each agent owns its worktree snapshot. Nothing shared and mutable
crosses a thread boundary.

## S19 — the most dangerous interaction in the design

Two partitions are declared disjoint because their radii don't intersect — but
the radii come from a graph that misses edges. Two agents can collide through
an edge the index never saw, and the failure is silent and confusing: both
partitions pass locally, the integrated result breaks, and nothing explains
why. It converts an honest incompleteness into an apparent nondeterminism.

The three-part patch, all of which the v0.1 numbers make *more* urgent, not
less:

1. **Any symbol with `Unresolved` or `Candidates` incoming edges is
   unpartitionable** — it and its dependents go into one partition,
   conservatively. **Built and property-tested.**
2. **Partition-local checks never substitute for the integrated full check.**
   Optimistic partitioning, pessimistic integration. Documented; enforced when
   integration is built.
3. **When an integrated check fails after clean partition checks**, record it
   in the trail as a **suspected recall gap** with the symbols involved, and
   feed those cases back into the S1 measurement. Over time that becomes the
   best real-world recall signal available.

### What v0.1 says about how expensive rule 1 now is

Recall is **72.0%** and the resolver emits `Candidates` far more often than it
used to — deliberately, because a declared type is an upper bound and subclass
overrides are real. On the benchmark corpus, ambiguous edges rose from 35 to
several hundred once receiver typing landed.

Every one of those makes a symbol unpartitionable. Rule 1 is correct and it is
also, on this evidence, going to serialize a great deal. **Measure the
decomposition ratio before building N>1** — what fraction of real changes
partition into more than one group at all (S5). If it is low, multi-agent mode
is a large amount of machinery for a rare case, and that is a finding worth
having before the work rather than after.

## S18 — throughput is bounded by the backend, not the harness

N agents against one local model queue on one GPU. llama.cpp and Ollama are
built for batch-size-1 single-user work and degrade under concurrency; vLLM
and SGLang do continuous batching and are built for it.

A user running four agents against Ollama will see no speedup, may see worse,
and will blame TRELLIS.

- Probe the backend's batching capability at startup.
- Report it in `trellis doctor`.
- `--agents auto` derives from **measured backend capacity**, never CPU count.
- Degrade to sequential agents on a non-batching backend and **say so**.
- Document supported serving stacks for multi-agent mode as a separate matrix
  from single-agent mode.

`trellis doctor` currently reports `BatchingCapability::Unknown` and says it is
a default rather than a measurement — the pessimistic default, which is the
right one until probing exists.

---

## Budgets divide, they don't multiply

The global per-run ceiling is split across partitions, not granted to each. N
agents on a runaway loop is an N-times faster way to spend the user's money.
Track per-partition spend in `tracing` spans nested under the run span.

Wall-clock is the exception and is shared rather than divided, because
partitions run concurrently (A-20).

---

## Failure semantics

Because partitions are radius-disjoint, partial success is meaningful.

- **`all-or-nothing`** (default) — any partition failing rolls back the whole
  run. Safest, and correct under partial recall.
- **`land-clean`** — successful partitions land; failed ones are reported with
  their worktrees preserved. Only valid when the integrated check passes on the
  landed subset.

Never let a failed partition's work land partially.

---

## Preconditions

Do not start this milestone until:

- v1.0 ships, including the recall gate.
- Single-agent cost and wall-clock per change are measured. You cannot tune
  partition size or agent count without knowing what one agent costs.
- The decomposition ratio is measured on real tasks.

## Exit gate

- [ ] A task decomposing into three or more disjoint partitions completes correctly in parallel.
- [ ] A deliberately-induced cross-partition collision is caught by the integrated check and recorded as a suspected recall gap.
- [ ] No agent produces a verdict on another agent's output; an ADR says why.
- [ ] Symbols with unresolved or candidate incoming edges are unpartitionable.
- [ ] Partition-local passes never skip the integrated check.
- [ ] Integration order is deterministic and a failure is reproducible.
- [ ] Budgets divide across partitions; the run total is a rollup.
- [ ] `trellis doctor` reports backend batching capability and the multi-agent support tier.
- [ ] `--agents auto` derives from measured backend capacity.
- [ ] Non-batching backends degrade to sequential with an explicit message.
- [ ] A failed partition's work never lands partially.
- [ ] Measured speedup on the benchmark repo, reported honestly against the decomposition ratio.
