# v1.0 — The Harness

The version you use daily. Little new capability; mostly proving that what exists is trustworthy, and making the failure paths boring.

**Prerequisite:** v0.3 shipped. The wedge has been demonstrated at least once.

---

## Goal

Meet five conditions, none of them softened. They are the contract v1.0 makes with a user.

---

## The gate

| # | Condition | How it's proven |
|---|---|---|
| 1 | Recall on the benchmark repo meets the v0.1 threshold | Re-run the measurement harness against current code |
| 2 | Zero unsound edges — every `Resolved` edge is real | Full audit of the benchmark corpus, not a sample |
| 3 | A real change runs to human approval with a complete trail and grounded checks | End-to-end run, artifacts inspected |
| 4 | Induced mid-run failure returns the repo to its exact pre-run state | CI test, multiple injection points |
| 5 | Resumption works | Day-later resumption with no re-explaining |

Plus: acceptable operation on a local open-weight model at or above the v0.1 floor, via constrained tool calling.

Condition 2 is stricter than condition 1 and deserves attention. Recall is allowed to be partial — that's Constraint 1. Precision is not. A single unsound `Resolved` edge is a bug, because the whole product rests on "if we say it's connected, it is."

---

## Scope

**In:** hardening, degradation UX, `trellis doctor` completion, packaging, documentation, the gate proofs.

**Out:** multi-agent (v1.1), semantic backstop unless v0.1 triggered it, new languages, anything networked.

## What you build

### 1. Degradation UX (S6)

The biggest remaining product risk, and it is a UI problem rather than an engineering one.

Partial coverage will be routine — Constraint 1 guarantees it. Whether that reads as *honest* or as *useless* is decided entirely by how it's surfaced. A user who sees "2 unresolved" on every single run will stop reading it within a day.

Design for the tenth partial-coverage run in an hour, not the first:

- **Summarize, don't enumerate.** "47 resolved, 3 candidates, 2 unresolved (decorator indirection)" on one line. Detail on request.
- **Make the reason actionable.** `DecoratorIndirection` on a specific symbol should offer: inspect the candidates, add a test that covers it, or proceed with the gap recorded.
- **Differentiate severity.** An unresolved edge on a symbol nobody is changing is noise. One on the symbol being edited is the headline.
- **Never block on it.** Unresolved edges attach a coverage warning to the *approval*, not a halt to the *run*. A tool that stops ten times an hour gets switched off.

Three one-key paths at the approval prompt: proceed with gaps recorded, inspect candidates, add a test.

### 2. Precision audit

Condition 2 needs a full audit, not the sample from v0.1. Every `Resolved` edge on the benchmark corpus, verified.

This is expensive, so automate what you can: for each `Resolved` edge, mechanically check that the target definition exists, that the name matches after alias resolution, and that the import path actually connects the two files. Hand-audit the residue where mechanical verification is ambiguous.

Any unsound edge found is a bug fix plus a regression test, not a threshold adjustment.

### 3. Rollback hardening

Condition 4 needs more than the single induced panic from v0.2. Inject failure at each stage and prove clean restoration:

- Mid-edit, between two file writes.
- During a check subprocess, with the subprocess killed.
- After checks pass, before approval.
- During trail write.
- Orchestrator task panic.
- SIGINT from the user mid-run.

The last two matter most and are the ones usually missed. A panicking orchestrator task must not leave a half-applied change set, and Ctrl-C is how users will actually abort.

Also handle: what if `git reset --hard` itself fails? Disk full, permissions, a lock held by another process. Report loudly and leave the worktree path so the user can recover manually. Never fail silently on the recovery path.

### 4. `trellis doctor` completion

The one-stop diagnostic. Reports and explains:

```
Model       qwen-coder-14b @ Q5_K_M via vLLM
Tier        3 (harness-side constraint)  ✓
Floor       above measured minimum        ✓
Typecheck   pyright 1.1.x                 ✓
Tests       pytest, coverage available    ✓
Index       48,102 symbols · 91.3% resolved · built 2m ago
Worktree    clean                         ✓
Budget      medium (12 iter / 20min / 150k tok)
```

Every line that can be wrong should say what to do about it. A user on tier 4 needs to know they're degraded and what would fix it (**S17**).

### 5. Packaging and first-run

- Single binary, cross-compiled for the platforms you support.
- `trellis init` scaffolds `.trellis/` with a commented config.
- First run detects missing prerequisites — no type checker configured, no tests, dirty worktree — and explains rather than failing.
- The clean-worktree requirement needs a good error message. It is the first wall users hit.

### 6. Documentation

Write for someone who has never seen this. The two things that must be unmistakable:

- **Coverage is partial and here's why.** Users who understand Constraint 1 forgive unresolved edges. Users who don't feel misled.
- **`Verified` versus `Reviewed`.** The first time something breaks after a clean run, this wording decides whether the user feels informed or lied to (**S3**). Say it plainly in the docs and at the approval prompt.

### 7. Positioning honesty (S15)

The index is not a moat. Aider's tree-sitter repo map, a wave of MCP code-graph and blast-radius tools, Sourcegraph, and GitHub's own code navigation all occupy this space.

Write `MISSION.md` to concede that and argue the wedge where it actually is: grounded verification, clean rollback, bounded budgets, and the committed trail. Building the index yourself is justified by fit and simplicity, not by differentiation. A README claiming a novel code graph will be correctly dismissed by anyone who's seen the alternatives.

## Soft spots touched

**S2** partial recall, surfaced honestly · **S3** verified versus reviewed in docs and UI · **S6** degradation UX · **S9** the scale claim — state the supported range, don't claim a million lines without measuring · **S15** positioning · **S17** tier reporting

---

## On the scale claim (S9)

Parsing scales fine — tree-sitter runs at roughly 90+ source lines per millisecond and reparses incrementally. Resolution, memory, and index storage have no published numbers at a million lines for any Python tool, and you will not have measured it either.

State the supported range as what you tested: 100k–300k lines. Treat a million as a stretch target requiring sharding. A claim you haven't measured is the kind of thing that produces a bug report you can't reproduce and a user who stops trusting the rest of the README.

---

## The thing most likely to go wrong

Gate condition 1 fails on re-measurement. Recall drifted down because six months of resolver changes optimized for the cases you were looking at, and the benchmark was only run once, at the start.

Fix this before it happens: put the measurement harness in CI from v0.2, running against the benchmark repo on every merge to main. Recall becomes a tracked metric with a regression threshold rather than a number from a spike you half-remember.
