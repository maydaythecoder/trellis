# v0.2 — The loop

**Exit condition:** one real change on the benchmark repository runs end to
end, and an induced mid-run failure rolls back cleanly.

Status: **exit condition demonstrated, with judgement stubbed.** Built
2026-09-19: the orchestrator actor, the agent loop, `.trellis/config.toml`
loading, a scripted model, and `trellis run` with rollback.

**Both halves of the exit condition now run**, on a real git repository with
real mypy:

```
$ trellis run --model scripted:fix.json "fix the type error in calc.py"
snapshot at ad177cf...
   1. BlastRadius { symbol: "describe" }
   2. RunChecks { kinds: [Typecheck] }   check FAILED
   3. Edit { path: "app/calc.py", ... }
   4. RunChecks { kinds: [Typecheck] }   check passed
CONVERGED after 4 iterations, 1 checks passed.
```

```
$ trellis run --model scripted:bad.json "improve it"
   1. Edit { path: "app/calc.py", ... }
   2. RunChecks { kinds: [Typecheck] }   check FAILED
NOT CONVERGED after 2 iterations.
  the model stopped without a passing check. Its own summary was: I believe
  this is correct. Nothing was accepted, because only an executed check can
  accept it.
Rolled back to 26a056b.... Worktree restored: true.
```

The second is the architecture working. The model asserted success, an
executed check disagreed, and the tree came back byte-identical — `git status`
reports zero modified files afterwards.

**What is still missing: judgement.** A scripted model exercises real files,
real checks and real rollback, and stubs the only part that needs a model. No
result obtained this way is a model floor (S7), and the milestone is not
finished until the adapter exists.

**The adapter is now built** (tiers 2 and 4):

```
trellis run --model llamacpp:http://127.0.0.1:8080 "<task>"
trellis run --model vllm:http://127.0.0.1:8000 "<task>"
trellis run --model sglang:http://127.0.0.1:30000 "<task>" --unconstrained
```

Each dialect is a separate request shape with its own test, because **runtimes
silently ignore parameters they do not recognise**. A misnamed guided-decoding
key therefore produces *unconstrained* generation that is indistinguishable
from success until the model emits malformed JSON under load — so llama.cpp's
`json_schema`, vLLM's `guided_json` and SGLang's `sampling_params.json_schema`
are each asserted, along with the fact that tier 4 leaks no schema key at all.

Tested against an in-process stub HTTP server, so request shape and response
parsing are verified without llama.cpp installed.

`resume` and `partitions` are implemented (v0.3, CLAUDE.md). Local models have
driven the loop since 2026-09-20; see BENCHMARK_AND_EVAL.md §5.

v0.1 also left the **model floor** unmeasured, because it needs inference.
That measurement was made here — four configurations, the floor located only
at tier 4 (`qwen3:8b` Q4_K_M on Ollama repaired 5 of 20), not under constrained
decoding (BENCHMARK_AND_EVAL.md §5.7) — and is a precondition for trusting anything the
loop does on local weights.

## 1. The grounding contract comes first

Build this before the loop, not after. Under delivery pressure it is the first
thing that gets softened, and softening it silently removes the only reason to
believe any result.

```rust
// trellis-checks/src/verdict.rs
pub struct Verdict {
    passed: bool,
    detail: CheckDetail,
    _seal: Seal,          // private unit struct — outside crates cannot construct
}
```

Three `pub(crate)` constructors, each taking a `ProcessOutput` from a process
that actually ran: `from_typecheck`, `from_tests`, `from_import`. The model's
result type has **no pass variant**:

```rust
pub enum ToolResult {
    Radius(RadiusReport),
    Checks(Verdict),        // came from trellis-checks, cannot be forged
    FileContent(String),
    Edit(EditOutcome),
    Error(String),
}
```

There is no code path by which model output becomes a `Verdict`. Making one
requires deleting a private field and changing a crate boundary — loud enough
to notice in review. That is the point.

**Already built and holding:** the seal, the `ToolResult` shape, and the
decision that `Verdict` derives `Serialize` but **not** `Deserialize` — a
derived `Deserialize` would be a public constructor from arbitrary JSON and
would defeat the seal (A-17, ADR 0004).

## 2. The loop shape — **built**

One model, a flat tool list, iterating. The blast radius and the checks are
**tools it calls**, not stages in a pipeline written for it.

| Tool | Args | Returns |
|---|---|---|
| `blast_radius` | `{ symbol }` | `Radius(RadiusReport)` — reach *and* coverage |
| `read_file` | `{ path }` | `FileContent(String)` |
| `edit` | `{ path, old, new }` | `Edit(EditOutcome)` |
| `run_checks` | `{ paths, kinds }` | `Checks(Verdict)` |

Not a verification fan-out, and not a committee. ADR 0005 says why: Constraint
2 means parallel judgment multiplies error. Sub-agents exist for context
isolation on separable subtasks — that is delegation, not review.

**Where Constraint 2 actually bites.** The model may emit `Step::Done`. The
loop then asks the checks, and records convergence only if the most recent
executed check passed. The chain runs `last_check_passed` →
`Turn::verdict_passed` → `ToolResult::Checks(Verdict)`, and a `Verdict` is
constructible only inside `trellis-checks` from a process that ran. An agent
declaring success having run nothing is not recorded as having succeeded, and
that is a test.

"Most recent" rather than "any", deliberately: a check that passed before the
last edit says nothing about the tree as it now stands.

Budget exhaustion escalates exactly once and tells the model that turn is its
last — otherwise escalation is a wasted iteration.

## 3. The orchestrator — **built**

Single-owner actor. It owns the `Index` outright: no `Arc<RwLock<Index>>`, no
shared mutable graph. Everything else sends messages over `tokio::sync::mpsc`
and awaits a `oneshot` reply.

This gives write/check serialization for free, without a lock anyone can
forget to take. The cost is that a wide change serializes, which is a real
ceiling to **measure** (S5), not assume away.

Three behaviours are tests rather than intentions:

- **An edit reindexes the file it touched.** A stale graph would let the next
  blast radius describe code that no longer exists.
- **An edit anchor must occur exactly once**, or nothing is written. The model
  cannot check this for itself without reading the file it is about to change.
- **Absolute paths and `..` are refused**, for reads and writes alike. The
  grammar guarantees a well-formed path string, not one inside the tree that
  rollback covers (S7 metric 3).

## 4. The model adapter

`llguidance` is the single grammar authority — a Rust crate, so it embeds with
no FFI to a Python stack. Tool argument structs derive `schemars::JsonSchema`;
the derived schema compiles to a grammar. No hand-written BNF.

Four tiers, probed at startup:

1. **Native tool calling** — the model's own function-calling API.
2. **Runtime-side constraint** — hand the grammar to llama.cpp / vLLM / SGLang.
3. **Harness-side constraint** — TRELLIS owns the sampling loop and applies the
   mask itself. The default for local open weights, and what makes any model
   work regardless of what it was trained for.
4. **Validate-and-retry** — opaque API with neither. Lossy, slow, warn loudly.

**Already verified:** llguidance 1.8.0 is MIT and actively maintained; the
schemars → JSON Schema → llguidance path compiles real derived schemas. Also
recorded: the brief's three-call embedding sketch omits `CommitResult`'s
`backtrack` and `ff_tokens`, and neither is optional — fast-forward tokens are
throughput, backtracking is correctness.

**Settled by ADR 0013 (S17 closed):** build **tiers 2 and 4 only**; defer
tier 3 entirely.

The reason is that llguidance is already the grammar engine inside llama.cpp,
vLLM and SGLang, and the grammar TRELLIS compiles is the same artefact whether
it masks locally or ships it to the runtime. For the runtimes local users
actually run, tier 2 delivers what tier 3 delivers with no inference code in
TRELLIS at all. Tier 3's remaining value is confined to runtimes exposing
logits but not guided decoding.

When tier 3 is eventually built it uses `candle`, not `llama-cpp-2`. That
reverses an earlier draft, on evidence: this machine has no cmake, no compiler
and no CUDA toolkit, so `llama-cpp-2` cannot be built on it at all, while a
`candle` + `llguidance` crate built clean in 5m30s. `cargo build` on a clean
machine is the distribution story.

**Consequence for this milestone:** the largest unestimated item is gone. The
adapter is schema → grammar → the runtime's guided-decoding parameter, plus a
validate-and-retry fallback that warns loudly.

Why this matters more than it looks: **quantization degrades format
reliability faster than it degrades reasoning.** A 14B quant may reason
adequately about the code and still emit malformed tool calls. Grammar
constraint deletes that failure mode rather than papering over it with retries.

## 5. The model floor (S7), carried over from v0.1

Constrained decoding guarantees a well-formed call, not a sensible one. A 3B
model will reliably emit valid JSON calling the wrong function. The floor is
about judgment, not format.

A spike across sizes and quantization levels, all under constraint, on 20–30
real tasks from the benchmark repository. Seven metrics, in priority order:

1. **Check-recovery rate — the primary signal.** Given a failing type check or
   test, does the next iteration reduce the failure count? The whole
   architecture rests on this. Measure failures resolved per iteration, and
   the rate of iterations that *increase* failures.
2. **Task completion rate.** The headline, but lagging.
3. **Argument correctness.** The grammar guarantees a well-formed path string,
   not an existing file. Grade against a gold trace.
4. **Termination discipline, both directions.** Stopping early and looping past
   progress are different failures with different fixes.
5. **Run-to-run variance.** Five runs per task; set the floor on the worst case
   or p25. A floor set on a mean is a lie.
6. **Context degradation.** Same task at 25/50/75% window fill. This sets the
   context budget in S5.
7. **Wall-clock per task**, including constraint overhead.

Report the floor as a **configuration** — model × quantization × runtime — not
a parameter count. "7B minimum" tells a user nothing.

## 6. Rollback

Git-backed and boring. Require a clean worktree, record `HEAD`, let the
orchestrator be the only writer, and on any failure or budget exhaustion
`git reset --hard` plus cleaning untracked files the run created.

Requiring a clean worktree is a real constraint on the user and the right
trade: snapshotting and restoring a dirty tree is a source of data-loss bugs
in the one path that has to be reliable.

**Already built:** snapshot/rollback in `trellis-vcs`, verified by an induced
mid-run panic in the test suite. CI runs it as the `rollback-gate` job in `.github/workflows/ci.yml`.

---

## 7. Budgets

Hard per-run ceilings on iterations, wall-clock and tokens, read from
`.trellis/config.toml`, tracked through `tracing` spans so accounting and
observability are one mechanism. On exhaustion: escalate once with current
state, then roll back.

The cost profile inverts by configuration and the budget code must know which
it is in — on a frontier API tokens are scarce; on local weights marginal
token cost approaches zero and **wall-clock** is the budget. Keys are the
user's, so a runaway loop spends their money: the global ceiling applies
regardless of tier.

Current defaults (40 iterations, 20 min, 2M tokens) are **placeholders, not
measurements**, and are marked as such in source. Calibration comes from real
usage (S8).

## 8. What v0.1 hands this milestone

- A resolver at **72.0% recall, 100% precision** — good enough for
  `blast_radius` to be a real tool, not good enough for the v1.0 claim.
- A **hard problem in the degradation UX**: `trellis radius Factory` reports
  92 resolved call sites beside 2,382 unresolved ones. The loop will surface
  this on every radius call. S6 is a v0.3 blocker and the loop's context
  selector has to assume it.
- `.trellis/index.bin` persistence, so the loop does not rebuild the index per
  tool call (~120 ms → 48 ms warm).

## 9. Measurements to start collecting now

These feed v1.0 and v1.1 and cannot be reconstructed later.

- **Call-sites-to-wall-clock.** How run time grows with blast-radius size. Sets the practical ceiling (**S5**).
- **Call-sites-to-context.** How much window a wide change consumes. Constrains the selector.
- **Check cost.** Wall-clock per typecheck and per test run, scoped versus full.
- **Decomposition ratio.** What fraction of real tasks would partition into more than one disjoint group at all. If it's low, v1.1 is worth less than it looks.
- **Iterations to convergence**, and the rate of iterations that increase failure count.
