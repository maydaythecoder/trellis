# v0.3 — Memory

**Exit condition:** the wedge, demonstrated once. Reopen a repository, say
what's next, re-explain nothing.

Status: **trail and resume built** (2026-09-20). A run records what happened,
commits it, and `trellis resume` reads it back. Still missing: context-file
and governance import, and feeding prior context into the loop as a starting
state.

Three problems surfaced only by running it, each now a test:

1. **The trail must be written after rollback.** Rollback is `reset --hard`
   plus `clean -fd`, and `.trellis/runs/` is inside the repository — so a
   trail written first is deleted by the rollback, losing the record of
   exactly the run worth recording.
2. **The trail must be committed, not merely written.** Untracked, the
   worktree would never be clean again so no later run could start, and the
   next rollback's clean would delete every accumulated trail. Only the trail
   is staged; the code a run proposed stays uncommitted because accepting it
   is the user's decision.
3. **Second-precision timestamps ordered two same-second trails by slug**, so
   `resume` read whichever task name sorted last rather than the most recent
   run. A resume that silently loads the wrong session is worse than one that
   finds nothing.

This is the milestone the product is actually for. Everything before it makes
a change safe; this is what makes the *next* change cheap.

## 1. The trail

One JSON document per run, committed under
`.trellis/runs/<timestamp>-<slug>.json`, with two structurally separate
sections:

```jsonc
{
  "task": "...",
  "factual": {              // what happened. Machine-checkable.
    "proposed": [...],
    "radius": { "resolved": 47, "candidates": 3, "unresolved": 2 },
    "checks": [ { "kind": "tests", "passed": true, "detail": "..." } ],
    "approved_by": "human",
    "mode_counts": { "verified": 45, "reviewed": 7 }
  },
  "judgment": {             // the model's opinion. Speculation, labeled.
    "tech_debt_projection": "...",
    "rationale": "..."
  }
}
```

**The split is the whole point.** Future agents read the trail as context. An
errant judgment entry otherwise propagates indefinitely, gaining authority
with each run that quotes it. Keeping speculation in its own section, labeled,
is what stops a guess becoming a fact by repetition (S11).

**Already built:** the format, and the decision that `Verdict` serializes but
does not deserialize — trails read back as inert `RecordedCheck`, never as
something that can assert a pass.

---

## 2. Trails are untrusted on read-back

A trail lives in a repository that may take contributions. Reading one is
reading attacker-influenceable text into an agent's context (S10).

**Already built:** trails read back as a distinct `UntrustedTrail` type
(A-18), so every use site sees the untrustedness in the type rather than
having to remember it.

Still to do: provenance per entry, and hashing the factual section so
tampering with it is detectable rather than merely discouraged.

---

## 3. `Verified` and `Reviewed` are never one number

Two audit modes, both surfaced:

- **`Verified`** — a check covered this call site and passed.
- **`Reviewed`** — no test covers it; the model read it and did not object.
  A weak signal, labeled as one, counted separately.

`ModeCounts` has no `total()` on purpose (ADR 0003). The first time something
breaks after a clean run, this wording decides whether the user feels informed
or lied to (S3).

---

## 4. Context import and resume

**Built:** `trellis resume` finds the newest trail and prints its recorded
context — task, radius counts, audit split, checks, and the previous run's
judgment, fenced.

**Not built yet:**

- **Context file** — the repository's own conventions, commands, and rules,
  imported once and carried into every run.
- **Governance rule import** — project rules the loop must respect, read from
  the repository rather than configured per session.
- **Feeding prior context into the loop.** `resume` currently reports; it does
  not yet seed a new run's `Transcript` with what the last one established.
  That is the difference between "re-explain nothing to yourself" and
  "re-explain nothing to the agent", and only the second finishes the wedge.

---

## 5. S6 lands here, and it is not optional

The degradation UX was scheduled for v1.x. The v0.1 measurements moved it:
`trellis radius Factory` reports **92 resolved call sites beside 2,382
unresolved ones** in the files it touches.

That is the honest report — S2 requires it, and Q-13 exists because
suppressing it was worse — and 2,382 items is not a list a user skims and
dismisses. It is a screen they close. The original failure scenario assumed
the honesty mechanism would erode over ten runs; the measurement says it fails
on first contact.

What has to be designed, with real numbers in hand:

- Aggregate repeated reasons across a session rather than re-reporting per run.
- Collapse the unresolved list with a stable count in view.
- Three one-click paths: proceed with gaps recorded in the trail, inspect
  candidates, or **add a test** that converts a `Reviewed` site into a
  `Verified` one. The third is the only one that improves the repository, so
  it should be the cheapest to take.

Open: whether repeat suppression is per-session or persisted in `.trellis/`.
Persisting is more useful and also a way to permanently hide a warning (Q-6).
