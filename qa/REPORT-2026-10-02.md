# QA Run — 2026-10-02: `trellis tui` on a Linux pty

The interface that ships: `trellis tui` (the tui-demo `AppState` fed by the
real loop through `tui_bridge`), built from commit **`2025b1c`** (branch
`drain`) and driven through tmux. The 2026-09-21 pass exercised `chat`, not
this. Ticket #15.

## Verdict

The terminal is handled correctly on every path tried. Resize at three static
sizes and twice mid-stream, shrinking below the minimum and growing back,
Ctrl-C mid-run and an induced panic all left a usable terminal. Ten minutes of
back-to-back runs held the process at 24.1–24.5 MB RSS after its first 5 s.

What the interface **says** is less sound. Four things on screen are wrong or
missing, and the first one cost this pass a wrong diagnosis:

1. **The end of a run can be invisible.** The transcript does not follow its
   own output. After nine runs it still showed run 1's opening lines. Nothing
   else marks a finished run: the budget line keeps its last iteration and
   the header keeps its last worktree state. A run that ended with `trail
   written but not committed` looked like a run frozen at iteration 3. It was
   read that way here for several minutes before a scripted run showed the
   message sitting below the visible area.
2. **The budget line's ceiling is the mock's.** `iteration 3/4` is
   `ITERATION_CEILING = 4` in `tui-demo/src/tui/view.rs`, commented "The mock
   runs four iterations". The real default is 40.
3. **`elapsed` is always `0s`.** `tui_bridge.rs` emits `elapsed_secs: 0` on
   every `BudgetUpdated`.
4. **`tokens` is prompt bytes.** The same event passes `f.prompt_bytes` as
   `tokens`. The CLI labels the same figure `B first prompt`.

Items 2–4 are a budget line that shows three figures and gets all three wrong.
That is the kind of display CLAUDE.md's "no fabricated figures" exists to stop.
None was fixed here (this ticket is a measurement), and each is filed; see
"Filed".

### Sustained load: what the run counts do not show

The harness waited up to 180 s for each run's trail commit, then hard-reset
the worktree and submitted the next task. Three of nine runs outlasted the
wait. The harness then reset the worktree **under a run that was still going**,
and typed the next task into the input while that run was still going, which
is why the last screen shows `> afix the describe annotation`: a leftover `a`
from the too-small row plus the next task. So nothing here says how many of
the nine runs completed or how they ended. The RSS and responsiveness figures
are unaffected: they are measurements of the process, which stayed up
throughout.

### A diagnosis this pass got wrong, and how it was corrected

The first live run looked frozen: `iteration 3/4 · 2435 tokens · 0s elapsed`
for several minutes, the process asleep with no child and no socket to
Ollama, and a trail staged but not committed. Git in this WSL account has no
identity, and a commit there fails, so the conclusion was that the TUI had
hung on the failed trail commit without saying so. That was wrong.

Reproduced deterministically with the scripted model
(`qa/fixtures/scripted-annotate.json`) in a clone with no identity:

- `trellis run` exits 1 within 1 s and prints `trail written but not
  committed: git command failed: git commit --only … fatal: empty ident name`.
- `trellis tui` prints the **same line in its transcript**
  (`15-no-git-identity-scripted.txt`). The run had ended. In the live run the
  line was below the visible part of the transcript, and the budget line
  stayed at `iteration 2/4 · 0 tokens · 0s elapsed` for the whole minute it
  was watched.

So the defect is item 1 of the verdict, not a hang. `08-run-ended-off-screen.txt`
is the screen that was misread. Both paths leave the trail staged in the
index after the failed commit, and the CLI says so.
